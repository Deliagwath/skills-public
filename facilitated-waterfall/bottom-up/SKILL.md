name: facilitated-waterfall-bottom-up
description: Works a concrete task or fix from the code up to the waterline — locates the code, climbs the abstraction ladder to check it sits in the right place against the governing docs, resolves at the line, implements below it, and reconciles what it learned back into the durable record. Hands product-level conflicts to product-waterfall direct or reflect. Records working memory in docs/probes/. Use when handed a bug, change request, a pointer to a named artifact, or a task rooted in existing code.
---

Take a concrete trigger — a bug, a change request, a task — and carry it up to the waterline from the code side. Find the quick fix, then **look up**: is it in the right spot, the right class, the right module, the right architecture? Settle where it belongs, honor the commitments above the line, implement below it, and feed what you learned back up. Read `conventions` for the drilling technique, the waterline, append-only, formats, and numbering — not repeated here.

The working document is a **Probe** (`docs/probes/<id>.md`) — the one mutable artifact, your working memory across sessions and context windows. Open it when there is something to carry (*When to open a probe*); once open, it carries the investigation so a fresh agent resumes from its header, not from zero.

## Ascent guard

You may change anything **below** the waterline freely — placement, class, module, pattern are reversible mechanism. You may **not** overturn a commitment **above** the line (an ADR decision, a Direction constraint or scope) without surfacing the trade-off and recording **accepted** supersession. If the trade-off isn't accepted, the fix is wrong — go back down and find a mechanism that honors the decision.

---

## When to open a probe

The climb (Phases 2–3) always runs. The probe file exists only when something must outlive this session (adr-0011). Work **without a probe** while all of these hold: the trigger is a concrete fix, this session can finish it, and every governing decision re-read so far still holds.

Open one with `sp new probe` (Phase 1) the moment any of these is true, and carry what the session already found into it, dated:

- a governing verdict comes out `amendment candidate`, or the fix needs an above-the-line or product-level change;
- an Open question, or the work itself, will outlive this session;
- the trigger is an artifact pointer, an `effect not achieved` line or a `sp log` record;
- the fix mutates live or deployed state, so the rollback point needs a home.

Where a phase below says to record something in the probe and none is open, hold it in the session. If it needs a second reader, that is the signal to open one.

**A probe-less close** skips Phase 5 and leaves three things:

- **The reply** states the read depth and the verdict on each governing doc. The rules of Phases 2–3 bind what is said exactly as they bind what is filed.
- **The commit message** says what changed and why, and names the governing ids.
- **A handbook entry**, only if the next session in this area would act differently knowing the lesson (`conventions` → Handbook → Deposit, step 1 alone: no promotion, no cut test). Its Source names the symbol and path.

A Task the fix completes still takes its ledger line. Write no Plan unless author-blind risk calls for one.

## Resuming an open probe

If the trigger names a probe that is already `open`, don't create a new one. Resume it. **Before any other action**, append a dated block recording what this session actually re-read, under its Findings — or at the file's true tail where the probe's earlier dated blocks already live (a file whose skeleton puts sections after Findings keeps its log in one place: the resume extends the established position, it never re-opens an earlier section mid-file):

```
**YYYY-MM-DD — Resumed.** Read depth:
- adr-0007 — FULL
- task-012 — PARTIAL (Goal only)
- direction-003 — NOT_READ (known from this probe's summary)
```

List every Governing doc. Anything you know only from the probe's own text is **inherited, not read**: mark it `NOT_READ`. The probe is testimony, not ground truth. Continue from the map, not from the summary's next step. This is a statement, not a gate: go on and re-read what the next step depends on. To re-read, take an inherit point (`conventions` → Handbook → Inherit) with `sp file` on the path the next step touches (or `sp tree <id>` on the artifact it touches), and put its budget line at the head of the block. The session that creates the probe states its read depth in Phase 2 instead. When the next step is a **wall-clock wait** — a carry that records and ends — the map goes all `NOT_READ`, justified per doc by the doc tree not having moved since the last full read (`git log --since <that read> -- <docs dir>` — the filter goes *before* `--`: a `--since` after `--` is just another pathspec and the window silently drops, and `git log` answers empty for a nonexistent path exactly as for an unmoved one, so confirm the paths exist before trusting an empty result), with an explicit *no verdict owed*: a wait's premises are world measurements (re-measure them, per the rule above), not doc text, so no full re-read of every governing doc is owed for a carry that only records and ends.

**Re-measure the premise, not just the text.** The read-depth map covers what the probe *read*; its dated Findings also carry *measurements of the world* — a cross-repo task's state, an installed tool's behavior, a live system, a test baseline. While the probe is blocked or parked those facts move: prerequisites ship, tools update, baselines shift. On resume, re-measure every premise the next step depends on and record the fresh numbers as dated findings (the same discipline the evidence-string rule in conventions applies to a ledger count). Re-measure means re-running the query: a number re-cited from an earlier finding with a "no change" stamp is a re-assertion, not a measurement — if the earlier line was wrong (a misremembered name, a stale value), the error propagates into the resume record the next wake inherits, so every number in the re-measurement block must come from a query this session. A fresh measurement that refutes an earlier finding does not rewrite it — the record stands, the refutation is appended — and a downstream artifact that still encodes the old premise is *named* stale in the probe (which line, what the fresh measurement says), not edited here: its correction belongs to the session that owns it, and a blocked one's to the session that unblocks it.

When the probe's place is the middle of a plan build — a stopped run recorded its built steps and its next step — the work to continue is the plan: load `implement` and run the plan's remaining steps from the probe's map. The resume re-measurement and the climb still run on entry; but the plan, not a fresh derivation, is the step list — do not re-plan, re-baseline, or re-drill a plan whose decisions the probe already carries.

## Phase 1 — Anchor

State the trigger and the candidate quick-fix in one or two lines. A trigger can be a pointer to a named artifact — a Direction, an Epic, or a probe, by id or by name, with or without a repo prefix. That is a real trigger, not an empty message: before asking the user for anything, resolve it to open work — `sp tree <id>` and `sp frontier` in the named repo (conventions → The `sp` script) — and resume the newest `open` probe under it per *Resuming an open probe*. Only if nothing open matches do you ask what they want done. A trigger can be a record from `sp log`, handed over by `debugging:improve-sp`: the call, its rerun line and the verdict that `sp` is at fault. Reproduce it from the rerun line before anything else; the fix goes in `sp` with a regression case in `test.sh` on the suite's fixture, never with the record's private paths. A trigger can also be an `effect not achieved` line in `docs/tasks/LEDGER.md`. In that case the Task's mechanics were verified but its intended effect did not show up in use, so climb from what was built to why it didn't work. If the Task serves a Story, the climb must reach the Story's Outcome: a wrong mechanism is fixed below the line, and a Story that can't hold goes to `direct` Refine (or a D-/X-entry to `reflect`), as in Phase 3. When a probe is due (*When to open a probe*), create it with `sp new probe "<title>" --relates <governing id>,…`: it writes the collision-free id (`probe-YYYY-MM-DD-slug`), `status: open` and the section skeleton, and prints the path (`conventions` → *The `sp` script*; without `sp`, write them by hand). Keep the title a few words — `sp` slugifies it into the id and the file name, and that id propagates into every link, command, and ledger line. Then fill the **Trigger** section. No authoring above the line yet.

## Phase 2 — Situate

Locate the code (`grep`/`find`/`git log`). When the trigger concerns **deployed or live state** (installed software, running services, pinned checkouts, a whole machine) rather than a code path, the code is the live system: take a **read-only inventory** — package-manager lists, install roots, `git status` of each pinned checkout, the live outdated list, service and process state, and the install or setup scripts that made each of them — and fold it into **Findings** dated, with the paths and commands. The docs tree records intent; the live system records what is actually declared and running, and the gap between them is often the finding itself. The same rule reaches stored *data* of a live stream — a queue, candidate or draft files, a JSON store: recompute the generator that wrote it today, classify each stored row as still-produced, stale, or superseded, and record the delta. A row carrying no provenance stamp (timestamp, source, the rule that made it) makes staleness unjudgeable, and that gap is itself a finding. The same rule reaches a *referenced* repo's working tree: when the inventory finds uncommitted work there, attribute it — mtime against your session's window, and a diff read for what it adds, since `sp` verbs normalize at most and never author prose — and record it as a dated finding. Never restore, commit, or build on it; a referenced repo is read-only ground, and its WIP is that workstream's to manage. **Inherit point:** `sp file <trigger path>` (`conventions` → Handbook → Inherit) gives the docs linked to it, ranked, with the handbook and the budget share. When the trigger names an artifact instead of a code path ("direction-021"), run `sp tree <id>` and `sp trace <id>` first: where it stands, what is under it, and what is next. `sp` is `~/.agent-skills/facilitated-waterfall/scripts/sp`, not on `PATH`: test that file, not `which sp`. Without it, the text rules there apply. Then walk `relates` **upward** from whatever artifact governs this area to collect every constraint — ADRs, the Task/Epic scope, the Direction. `sp` finds docs only on evidence, so the walk is what makes the set complete. Read what it finds by tier, constraint sections first (`sp show <id> Decision`, `sp show <id> Constraints "Out of scope"`). If the chain crosses into the product layer, keep walking: the Story, its product Epic/Direction, and the `docs/PRODUCT.md` D-/X-entries they cite. Record them in **Governing docs**. If none exist, write "code ahead of docs" — that is itself a finding to reconcile later.

Head the Governing docs section with the **intent trace**: one sentence per level, leaf to root, taken from each artifact's `intent:` along the first `relates` entry in list order that sits higher (`conventions` → Artifact formats). Where a level has none, write `<id>: no intent line`. Never compose one from the body. `sp trace <id>` derives it, showing a missing line as `(title)`. The trace is what the climb tests the fix against, so a gap there is worth knowing before Phase 3.

Below the trace, state the **read depth at entry** (`conventions` → Handbook → Inherit): the budget line, each doc as `FULL` / `PARTIAL` / `NOT_READ`, what was trimmed over the share, and any sealed doc opened and why.

## Phase 3 — Climb & deliberate

This is the heart, and it is the step most easily skipped — the pull toward a quick fix is to find a clean home for the code and start writing. Resist it. From the fix's natural home, climb the ladder one rung at a time, asking each rung's question. **Do not stop at the first rung where the change fits** — a clean below-the-line home is necessary but not sufficient. Always carry the climb all the way to the waterline and read the governing ADR(s) and Direction. The point of reaching the top is not to ask permission; it is to *test the recorded decision against what the code just told you*.

```
placement (right spot?) → class (right abstraction?) → module (right owner?)
→ architecture/pattern (consistent?) → ══ WATERLINE ══ → ADR / Direction (still true?)
→ ┄┄ seam ┄┄ Story (still achievable?) → ══ PRODUCT WATERLINE ══ → docs/PRODUCT.md (still true?)
```

The last two rungs exist only when a product layer governs this area (see `conventions` → Product layer). When it does, the climb reads them too.

**Explore the code before you conclude anything.** Read the code the fix touches *and* the code the governing ADR describes — reason from the source, not from the doc's summary of it. When the trigger **proposes a mechanism that already exists** in one or more forms — different dialects, layers, or repos — locate every existing instance, record them in **Findings**, and frame the proposal as unification or generalization rather than net-new: the governing decisions that constrain the existing instances constrain the proposal too, so they enter the climb even though the proposed code does not exist yet.

**An aggregate is a claim about the data, not the code — measure the data.** When the fix groups, counts, or rolls up records already in a stream or envelope, don't settle its placement from the producer's code alone: query the store the records land in and measure join and attribution completeness — the fraction of source rows the aggregate can attach to, and whether each record carries the fields the grouping keys on. A large unattributed or unjoined fraction makes a consumer-side roll-up structurally hollow however clean the consumer code, and a field the record lacks must be derived where the join happens, not in the consumer. Put the coverage number and its filter in Findings — what you counted, what you attached, what you dropped (the same filter rule the *Rules* section applies to ledger and doc-tree counts) — before the placement rung settles. **Inherit point:** on entering a module you haven't situated yet, `sp module <dir>` first. Record what you find in **Findings** (dated, append-only — what investigation revealed about reality). Record the climb in **Deliberation**: which rung each candidate settled or failed at, and whether the line was hit. Keep **Open questions** (each with "what would resolve it") and **Risk** (blast radius · rollback · cost-of-wrong) current as you go.

**Test each governing decision — don't just obey it.** For every ADR that governs this area, hold its Decision against your Findings and ask: are its Context and assumptions still true in the code as it stands today? Does the clean fix you found quietly contradict, erode, or route *around* the decision? A decision you can only satisfy by working around it is a signal the ADR may be stale — not that your fix is clever. Write an explicit verdict for each governing ADR in Deliberation — `still holds — <why>` or `amendment candidate — <what reality changed>` — **before** you resolve. A verdict is owed on a doc only if you actually re-read it this session: the read-depth map (Phase 2 at entry, or the resume block) decides — a doc marked `NOT_READ` takes no verdict, stays `NOT_READ`, and its re-read is a pending open question, not a settled rung. A `still holds` written on text you never read is the resume rule's inherited-not-read error re-armed through the verdict. Skipping straight from a below-the-line home to implementation without recording these verdicts is the drift this phase exists to prevent.

**Price a mutation into a pinned area before proposing it.** When the fix — or the operator act it depends on — lands in a path a recorded guard pins (a hash manifest over data, a recorded baseline, a sealed or pinned store), do not let **Risk** stay theoretical: copy the repo to a scratch directory (excluding VCS metadata), apply one simulated edit of the intended kind, and run the repo's own gate against the copy. Record the pin values before and after in Risk, and the gate's verdict as a dated Finding. Two consequences follow: a gate failure that would otherwise surface only after the mutation becomes a cost the decision can weigh; and a pinned area with no rebaseline path — a baseline that cannot be re-recorded once set — makes the mutation an above-the-line decision the operator accepts, not a mechanism you implement. When the mutation is an operator act you cannot run yourself, the scratch simulation is the only way to price it: show the cost in the probe before asking for the act.

**Resolve at the line:**
- **Fits below the line *and* every governing decision still holds** (verdicts recorded) → mechanism change. Proceed to implement. No ceremony.
- **Requires an above-the-line change** → classify it:
  - *Correction* (the recorded decision is simply wrong on contact with code) → surface the trade-off, get explicit acceptance, then append a **superseding ADR** through the `design` discipline (load `top-down` Phase 3), which writes both edges with `sp supersede <new adr> --of <old adr>`. Record the acceptance in Deliberation.
  - *Net-new intent* (a missing decision, Task, or Direction) → **load `top-down`** at the matching tier to author it properly, then resume:
    - Missing decision → `top-down` Phase 3 (ADR).
    - Missing work unit → `top-down` Phase 2 (Breakdown → Task).
    - Missing/mis-stated problem → `top-down` Phase 1 (Shape → Direction).
  For the **Direction** case, "then resume" means **reconcile the probe** (Phase 5), not implement: the probe is working memory for the *climb*, and the placed, bounded unit is now the Direction. Its build (Breakdown → Tasks → Plan) is a separate top-down descent that opens its own probe(s). Reconcile once the Direction is authored, any amendment is recorded, and every Open question is resolved or deferred — even though no Task or Plan sits under the Direction yet.
- **Requires a product-level change** (product layer only) → never resolve it with an ADR. Hand it to the PM:
  - *The Story can't hold* (Outcome, Acceptance, or Out of scope is wrong on contact with code, but no `docs/PRODUCT.md` entry is involved) → **load `product-waterfall` `direct`** Refine on the Story, passing this probe's Findings. Resume with its Revision, or with "Story holds", in which case find a mechanism that meets it.
  - *A product decision or exclusion is the obstacle* (a D-/X-entry) → **load `product-waterfall` `reflect`**, with this finding as the signal and this probe as `relates`. Resume on its verdict: `holds` means go back down and honour it; `superseded` means continue against the new decision.
  - Record the hand-off and its outcome in Deliberation.

**Autonomy scales to tier** (per `conventions` → Depth & autonomy): a **Direction**-level or product-level gap is intent — always interview the human. A **Task/ADR** gap whose answer is derivable from code + existing docs, you may drive autonomously, escalating only on genuine ambiguity.

## Phase 4 — Implement

Only below the line, only after Phase 3 resolves — meaning a per-ADR verdict is recorded and every `amendment candidate` has been carried through the Correction path, not deferred. Do not open a Plan while any governing ADR is still an unresolved amendment candidate. Derive the **Plan** from the Task + governing ADRs when the work needs step-decomposition, which is judged by author-blind risk, not importance (`conventions` → Depth & autonomy); write it with `sp new plan "<title>" --relates <task-id>,<adr-id>,…` (Context · Steps · Verification · Risk), then `sp check <plan-id>`. A Plan may span several sibling Tasks. **Inherit point:** before editing a file outside what Phases 2–3 situated, `sp file <path>`; its handbook gotchas are the reflexes for that move. Skeleton first, then body. **When the implementation is an operation on live or deployed state** — a service update, a config reload, a daemon restart — rather than a repo edit, two rules add: confirm the state transition actually happened (new PID / port / version, process alive and not crash-looping) *before* running any verification, because a silently failed apply step makes the verification measure the pre-change state — and the first read after a restart is cold, so re-run the smoke before calling it a failure. Record the rollback point (prior commit, prior config, prior version) in **Risk** at the moment of mutation, not when something later looks wrong. When an effect leg lives in a running service — an in-flight event, a fenced route, a log, a counter — `references/verifying-live-effect.md` is the recipe: which legs you drive yourself, which belong to the operator, and how to record the ones you cannot run. Append verification results to the Probe's Findings. Do not report done if any Verification item fails or any ADR decision is violated.

**A state-dependent suite is verified on a tree that reproduces the failure.** When a test's pass/fail depends on what the live tree happens to hold at run time — which items are open, which ledger lines exist, which fixture the scratch copy carries — green at HEAD is a property of the tree, not proof of the code: the fix may only pass because another session's commit left the state the old code could read. Pin a tree that reproduces the red, prove red→green on it, and run at HEAD too; if HEAD moves under the run, record the moved commits and re-verify at the new one. `references/verifying-test-suite.md` is the recipe: attribution by measurement, the pinned commit, the pair of runs, and the record.

**A new read path over live state is smoked against the real store before commit — and the stub is written in the store's shape.** A suite green on its own stub proves the code against a convenient shape, not against the data: a key the check reads may carry a value the fixture omits, and the store may carry a format trait the stub cannot express. Write the stub the way the live data actually reads (a key with its value, the real section shape), then run the new path from the worktree against the actual store, read-only, before the commit stands; when the smoke and the suite disagree, the store wins — fix the code to the shape the store has, and the fixture to match, never the other way around. `references/verifying-live-effect.md` carries the drive pattern and the read-only-door recipe.

## Phase 5 — Reconcile (the return path)

Distill the probe into durable record, then freeze it. The Probe cannot move to `reconciled` until **all** gates pass:

- Every **Open question** is resolved or explicitly deferred.
- Every Deliberation **conflict** is either fixed-in-code or recorded as a superseding ADR with accepted trade-off — never silently dropped. A product-level conflict is closed only by a Story Revision or a resolved `reflect` probe.
- Every **docs/CONTEXT.md** term the work touched is verified against the current code and updated if stale.
- The artifacts produced/updated are listed in **Reconciliation** (new/superseded ADR, updated Task, new Direction, CONTEXT entries), and their `relates` link back to this probe. **Name only edits you can still see on disk**: before writing "the Task's Notes were corrected" or similar, run `git status --porcelain -- <path>` (or `git diff --stat`) on it. A reconciliation written from a compacted summary can claim an edit that never landed — the file stays byte-identical to its last commit while the probe, the ledger line and the commit message all assert the change. Correct the claim in the probe as a dated finding, don't quietly drop the bullet.
- **The Task ledger states match the code, not the frontier's labels.** A `done` line requires the effect observed in use (adr-0003) — where the effect never showed up, write the honest `effect-not-achieved` line, never a stamped done. A Plan-less Task that was actually built is recorded `implemented` / `deferred` / `abandoned` (adr-0009), not routed to `/plan`. The frontier's `unplanned → /plan` / `awaiting` rows are a derived, stale-able signal: reconcile each against the code, not the label. Work that is genuinely open, or old / no-intent and possibly superseded, is left and surfaced for the human's supersede-or-plan call — never killed unilaterally. `sp` recipe: `references/reconcile-task-ledger.md`.
- **Deposit** is done (`conventions` → Handbook → Deposit at a close). The probe's lessons are deposited, entries it relied on are promoted, and the cut test has run if it was triggered. Reconciliation carries the Deposit line, which names what was added, promoted, demoted or retired, or says `nothing durable`. If `docs/handbook/` is missing and something is durable, create it as `note` Bootstrap does: five files, and an `index.md` with `last verified: never` and `last pruned: never · 0 entries`.

**The Reconciliation body records the map, not a recap.** A useful reconciliation has four legs, each answering a question a resuming reader would otherwise re-derive: (1) which Findings moved which clause above the line, and the exact artifact each delta was written into — amendments, supersessions, new ADRs — plus an explicit list of the verdicts re-checked and **unchanged**, so the reader can tell which commitments reality was tested against and held; (2) every Open question answered, or explicitly deferred with what would resolve it; (3) what this session changed, split above/below the line, naming what was deliberately *not* done (an operator-only act, a cross-repo leg, a live-service effect) so its absence is a decision, not a gap; (4) the rollback point. The four legs are the shape for a probe that carried a **fix**; a probe that carried a **build** — whose reconciliation judges what was built, not which clause moved — names the legs it answers instead: the trigger it was opened with (answered, or deferred with what would resolve it), the effect as observed in use (with the filter behind every count), the boundary (what this run touched and deliberately did not), the risk, the decision (the ledger lines written), and the deposit — the resuming-reader test is the invariant, not the leg count. A reconciliation that restates the plan without the finding→clause map leaves the next reader unable to tell which recorded decisions moved.

Close it with `sp ledger reconcile <probe-id> "<one-line outcome>"`: it appends `- <probe-id> — reconciled DATE — <outcome>` to `docs/probes/LEDGER.md` and sets `status: reconciled`. Without `sp`, do both by hand. Then run `sp check` on every artifact the probe produced, then the whole-graph check (`conventions` → Batch check), then the commit step (`conventions` → Commit): a reconciliation commits as one batch — the probe, the artifacts it produced, the amendments, the glossary entries, the ledger lines — after any prior uncommitted work in the repo has committed on its own. Before committing that prior work, verify it is actually prior work in *this* stream (`git diff -- <file>` against the last commit): a diff left by another workstream is a loose end to flag to its owner, not something to fold into your reconciliation commit. A probe abandoned (not worth pursuing) is set `status: abandoned` and kept as a "why we didn't" record.
## Rules

- Implementation lives below the waterline. Never overturn a commitment above it without recorded acceptance.
- **File tools resolve relative paths against the session CWD, which a terminal call in another repo can leave behind** — a cross-repo run (the probe in one repo, a referenced checkout in another) is the usual cause: a `patch`/`write_file` that "fails to read" a path inside a *different* repo was anchored on the wrong CWD, not on a missing file. Use absolute paths for file-tool calls aimed at a specific repo (or check the terminal result's `cwd` before the run's first file edit).
- Never jump from trigger to Plan. Phase 3 — explore the code, climb to the waterline, and record a verdict on every governing ADR — is mandatory, not optional, even when a clean below-the-line fix is obvious. Without a probe the verdicts go in the reply (*When to open a probe*); the climb is never what gets skipped.
- A quick fix that only works by routing around an ADR is evidence the decision may be stale — investigate and record an amendment candidate, don't quietly implement past it.
- **Judge effect against the text that governs now.** A `done` line claims the effect under the current governing Direction and Task — if one was amended after the work, the part that moved belongs to the taking-over artifact, and a stamp on the old boundary is premature.
- Don't hand-author above-the-line artifacts ad hoc — load `top-down` so they get the full drilling discipline.
- The probe is working memory: keep the header (Trigger · status · Governing docs · Open questions) accurate so any session resumes from it. If this session must end while the probe is still open — user away, command execution blocked, awaiting an observed effect — append the dated findings you already have and the pending open question to the probe *before* responding: the file, not the transcript, is what the resuming session inherits. The owed block is owed with the probe already reconciled too: a run that sealed its probe and is then stopped (a wall-clock limit, an external stop signal) appends one run-ends block after the Reconciliation — the stop reason, what landed this run, what remains on the frontier — and commits it. That is the one append a run makes to a probe after sealing: it records the run's end, not a change to the reconciliation; no later run appends to a reconciled probe.
- After a context compaction, re-read the exact region of a document before appending to it — a paraphrased anchor from a summarized context will not match; take the matcher's "did you mean" hint and re-anchor from the current text. Re-read it fresh even when your in-context copy looks exact: a `sp` run since your last read may have rewritten the file on disk (the `sp check` header prints `regenerated`; `conventions` → The `sp` script). If a patch's anchor is gone because the file was restructured, fall back to a whole `write_file` of the probe rather than a maze of re-anchored patches. A `patch` that reports a non-exact match landed by a fuzzy strategy may have shifted its boundary: read the diff it returns before the next edit to that file — a shifted span can drop or duplicate a line just outside your anchor, and a corrupted line in the probe poisons the session that resumes from it. When you hold the full current text and a clean tree, prefer one scripted pass over a sequence of fuzzy patches: each insertion anchored on one distinctive line, every anchor asserted to occur exactly once, all replacements applied, one write — a mismatch fails loud before any byte moves, and the dated blocks land atomically. "The full current text" must actually be the whole file: a paginating reader (read_file truncates past its ~100K-character budget on a line boundary and returns a next_offset) silently returns a prefix whose "tail" is a mid-file line — read the file raw in the script, and normalize the trailing newline before splitting (a trailing `\n` yields a phantom empty line, off-by-one in any line-count assert), so the anchor asserts run against the true tail; a probe that has carried many dated blocks routinely exceeds the budget. The same discipline reaches code you patched through the compaction: when a new test then fails, print the source of the function as it stands on disk and evaluate each condition in-process to find the one that fails — do not re-patch from a paraphrased memory of the patch, and do not patch the fixture to satisfy a code bug you have not located.
- **When in doubt about what a protocol verb does, read its source before calling it.** The task's summary of a verb's contract is what you got, not what it does: which items a block or commit touches, what it writes, what it returns is one function read away, and a malformed ledger or block write is expensive to undo.
- **A negative claim about the docs requires a topic search, not just a `relates` walk.** The walk follows declared edges; a governing artifact that was never linked — or that arrived after a parent probe ran — is invisible to it. Before recording "no Direction/ADR for X" anywhere (in the climb, or in a correction of a parent probe's claim), search the doc trees of every repo in the workspace for the topic and read the hits: `sp -C <repo> search "<topic>"` (adr-0011), which lists the live docs and counts the sealed ones. Add `--sealed` only when the question is about history — what was tried, what went wrong. Without `sp`, grep `docs/`. A parent probe's *conclusions* carry the same inherited-not-read caveat as its read-depth map: the current tree wins.
- **State the filter behind any count you take from a ledger or the doc tree.** Ledger lines and verification results mix machine-runnable checks with human-attested legs (an operator's browser check, a leg awaiting another Task); a bare total silently counts both. Report the filter with the number — what counted, what was attested, what was excluded — or the count overstates what is re-runnable.
- Reconcile before closing. An `open` probe with unresolved questions is drift `conventions` audit will flag.
